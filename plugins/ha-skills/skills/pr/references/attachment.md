# 설명 문서를 리뷰어에게 전달하는 방법

## 먼저: 검증된 사실 (2026-07-30 실측)

**1. `.html`은 GitHub 첨부 허용 확장자다.** zip으로 감쌀 필요 없다. 공식 문서의 허용 목록에 `.html`, `.htm`이 포함된다(코드 파일 범주). 파일당 25MB.

**2. 그런데 첨부 파일은 클릭하면 렌더되지 않고 다운로드된다.** 실제 첨부된 HTML의 응답 헤더를 확인한 결과:

```
$ curl -sIL https://github.com/user-attachments/files/30420934/index.html
content-type: text/html
content-disposition: attachment;filename=index.html   ← 브라우저가 다운로드로 처리
```

`Content-Disposition: attachment`가 붙으므로 브라우저는 무조건 내려받는다. GitHub이 자기 도메인에서 사용자가 올린 HTML을 실행시키지 않으려는 의도적 정책이다(XSS·피싱 방지). 우회 방법은 없다.

**3. 첨부 업로드는 API/CLI로 불가능하다.** REST/GraphQL, `gh` 모두 지원하지 않는다. 웹 UI에서 코멘트 입력창에 드래그&드롭하는 경로만 있다.

→ 결론: **첨부(attachment)로는 "클릭 즉시 열람"이 원리적으로 불가능하다.** 즉시 렌더를 원하면 첨부가 아니라 *렌더되는 링크*를 줘야 한다. 아래 표에서 골라라.

## 선택지 비교

| 방식 | 클릭 즉시 렌더 | 접근 범위 | 내가 자동 처리 가능 |
|---|---|---|---|
| A. Markdown으로 PR 코멘트 게시 | **O** (스크롤만 하면 보임) | 저장소 권한자 | O |
| B. Artifact(claude.ai) 퍼블리시 | **O** | 기본 비공개, 팀 공유 필요(외부) | O |
| C. secret gist + gistpreview | **O** | **URL 아는 누구나**(외부) | O |
| D. HTML 파일 직접 첨부 | X (다운로드 → 열기) | 저장소 권한자 | X (사용자가 드래그) |
| E. PR 브랜치에 커밋 | X (다운로드 → 열기) | 저장소 권한자 | O |

기본 선택:

- **비공개/사내 저장소 → A**(+ 전체 HTML을 원하면 D로 보조). 외부 업로드가 없고, 클릭 없이 바로 읽히고, 내가 자동으로 붙일 수 있다.
- **공개 저장소 → C**. HTML 원본을 그대로 즉시 렌더할 수 있다.
- 사내 저장소인데 인터랙티브 HTML을 꼭 링크로 열게 하고 싶다면 **B**를 쓰되, 외부 서비스 업로드라는 점을 사용자에게 먼저 확인한다.

## A. Markdown으로 PR 코멘트 게시 (비공개 저장소 기본)

가장 마찰이 없다. 리뷰어가 링크를 클릭하거나 파일을 내려받을 필요 없이 PR 대화창에서 그대로 읽는다.

```bash
gh pr comment <번호> --body-file <설명.md>
```

HTML의 어떤 요소가 어떻게 옮겨지는지:

| HTML 원본 | Markdown 대응 | 비고 |
|---|---|---|
| 다이어그램(HTML/CSS) | ` ```mermaid ` 코드블록 | GitHub이 네이티브 렌더한다 |
| 인터랙티브 퀴즈(JS) | `<details><summary>정답 보기</summary>` | 클릭해서 펼치는 것까지는 동작. 채점·피드백은 불가 |
| 긴 배경 설명 | `<details>`로 접어두기 | "이미 아는 사람은 건너뛰기" 구현 |
| 콜아웃 | `> [!NOTE]` / `> [!WARNING]` | GitHub alert 문법 |
| 코드블록 | 그대로 | 언어 지정해 하이라이팅 |

한계는 정직하게 알려라: JS 채점 퀴즈는 재현되지 않는다. 전체 인터랙티브 버전이 필요하면 HTML을 D로 함께 첨부하거나 B로 호스팅한다.

코멘트가 아주 길어지면(대략 화면 10스크롤 이상) 본문 대신 별도 코멘트로 올리고, 상단에 목차를 단다. 코멘트 1개 본문 한도는 65,536자다.

## B. Artifact(claude.ai) 퍼블리시

HTML 그대로, 링크 클릭 시 즉시 렌더. 품질이 가장 좋다. `artifact-design` 스킬을 먼저 로드하고 Artifact 도구로 퍼블리시한다.

- 기본 비공개다. 사용자가 claude.ai에서 팀에 공유해야 리뷰어가 열 수 있고, 같은 조직이 아닌 리뷰어는 접근할 수 없다.
- 외부 서비스 업로드다. 사내 코드라면 사용자에게 먼저 확인한다.
- PR에 링크를 넣을 때 "공유 설정 후 열립니다"를 함께 적어 리뷰어가 404로 헤매지 않게 한다.

## C. secret gist + gistpreview (공개 저장소 기본)

```bash
gh gist create "<html경로>" -d "PR #<번호> 설명 — <제목>"
# 출력 URL의 마지막 세그먼트가 gist ID
# 렌더 링크: https://gistpreview.github.io/?<gist_id>
```

- `gh gist create`는 `--public`을 주지 않으면 **기본이 secret**이다.
- **secret ≠ private.** 목록에 노출되지 않을 뿐 ID(URL)를 아는 누구나 로그인 없이 열 수 있고 공개 API로도 조회된다. 코드 구조가 담긴 문서이므로 사내 코드에는 사용자가 명시적으로 허용하지 않는 한 쓰지 않는다.
- gist raw는 `text/plain`으로 서빙되어 브라우저에서 렌더되지 않는다. 그래서 gistpreview(서드파티 정적 렌더러)가 필요하다. 서드파티가 문제면 A나 B로 간다.
- 정리: `gh gist delete <id>`.

## D. HTML 파일 직접 첨부

접근 제어가 저장소 권한과 같아지는 native 방식. 다운로드 후 로컬에서 열어야 하지만(2스텝), zip보다 한 단계 짧다.

사용자에게 안내할 문구: "PR 코멘트 입력창에 `<html 절대경로>` 파일을 드래그하면 첨부됩니다. 리뷰어는 내려받아 브라우저로 열면 됩니다."

- HTML이 자체 완결형(CSS·JS 인라인)이므로 내려받아 열면 그대로 동작한다. 인터랙티브 퀴즈까지 살아 있는 유일한 native 방식이다.
- 파일이 여러 개일 때만 zip으로 묶는다(`zip -j out.zip a.html b.html`). 단일 HTML이면 zip은 리뷰어 손만 더 가게 한다.

## E. PR 브랜치에 커밋

```bash
mkdir -p docs/pr-notes && cp "<html경로>" "docs/pr-notes/<YYYY-MM-DD>-<slug>.html"
```

- GitHub은 blob에서 HTML을 렌더하지 않으므로 리뷰어는 raw로 내려받아 열어야 한다. 공개 저장소라면 `https://htmlpreview.github.io/?<raw-url>`로 렌더 가능.
- diff에 큰 HTML이 끼어 리뷰 화면을 어지럽힌다. `.gitattributes`에 `*.html linguist-generated=true`를 주면 기본 접힘으로 표시된다.
- **커밋은 리뷰 대상 diff를 바꾸는 행위다.** 사용자가 저장소에 파일을 추가해도 된다고 하지 않았으면 임의로 쓰지 않는다.
- 문서를 Markdown으로 커밋하면 GitHub이 네이티브 렌더하므로, 저장소에 남길 거라면 HTML보다 Markdown이 낫다.

## 본문에 넣는 문구

```markdown
## 리뷰 도우미
- 읽는 순서: `<핵심 파일>` → `<그 다음>` → 나머지
- 넘겨도 되는 파일: `<자동 생성/lock 파일>`
- 심층 설명(배경·구조·코드 워크스루·퀴즈): 아래 코멘트 참고
  <또는> [문서 링크](URL) — 클릭하면 바로 열립니다
  <또는> 첨부한 `2026-07-30-<slug>.html`을 내려받아 브라우저로 열어주세요
```

링크가 만료·삭제되어도 리뷰가 가능하도록, 본문의 배경·목적·구현 방향은 항상 자립적으로 유지한다.
