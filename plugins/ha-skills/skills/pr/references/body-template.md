# PR 본문 템플릿

아래 구조를 기본으로 쓴다. `.github/pull_request_template.md`가 있으면 그 구조를 우선하고, 여기 내용은 각 항목을 채우는 기준으로만 쓴다.

**본문은 요점만 쓴다. 목표 분량은 40줄 이내, 스크롤 없이 한 화면.** 상세 설명(코드 워크스루, 파일별 해설, 대안 비교, 데이터 흐름)은 `explain-diff-html`로 만들어 PR 코멘트로 붙이므로 본문에 중복해서 쓰지 않는다.

**필수**: 한 줄 요약, 배경, 변경 내용, 확인 포인트, 검증, 상세 설명 안내.
**조건부**: 해당될 때만 넣는다. 해당 없으면 섹션 자체를 삭제한다(빈 섹션·"N/A" 금지).

---

## 제목

`<type>: <무엇을 어떻게 바꿨는지>` — 저장소 관례를 따른다(Conventional Commits를 쓰는 저장소면 `feat:`, `fix:`, `refactor:` 등).

- 명령형·현재형으로 쓴다. "로그인 세션 만료 시간을 30분으로 늘림" (O) / "늘렸습니다", "수정 작업" (X)
- 결과를 쓴다. 파일명이나 작업 자체가 아니라 사용자·시스템에 생기는 변화. "SessionService 수정" (X) / "세션 만료 후 재로그인 없이 이어지도록 갱신 토큰 발급" (O)
- 50자 안쪽. 이슈 번호는 제목이 아니라 본문에 넣는다.

## 본문

```markdown
<이 PR이 무엇을 하는지 한 문장. 제목의 반복이 아니라, 결과를 쓴다.>

관련 이슈: Closes #123

## 배경
<문제 진술 2~3문장. 현재 동작이 어떻고 그게 왜 문제인지, 누가 영향을 받는지.>
<이 PR 후 달라지는 상태를 마지막 한 문장으로. "안정성 개선"이 아니라 "동시 요청에서 중복 결제가 생기지 않는다".>
<도메인 용어는 첫 등장에서 한 줄 정의. 문제의 역사·조사 과정은 쓰지 않는다 — 심층 설명 몫.>

## 변경 내용
<논리 단위 3~6개. 파일이 많아도 불릿을 늘리지 말고 묶는다. 한 항목 한 줄, 하위 불릿 금지.>

- **<단위 이름>** (`path/to/file.ts`): <무엇을 어떻게>
- **<단위 이름>** (`path/to/other.ts`): <무엇을 어떻게>

<구현 판단 근거가 필요하면 여기 한 줄로 결론만. 예: "재시도 대신 멱등키를 택했다(이유는 아래 상세 설명).">

## 확인 포인트
<리뷰어가 판단해줘야 하는 것만. 없으면 섹션째 삭제한다. 최대 3개.>

- [ ] `<파일:라인>` — <무엇을 판단해줬으면 하는지, 질문 형태로>

## 검증
- 테스트: `<추가/수정한 테스트 케이스>` — <통과 여부>
- 수동 확인: <한 줄>
- 확인하지 못한 항목: <있으면 솔직히. 없으면 이 줄 삭제>

<재현 절차가 여러 단계라면 본문에 쓰지 말고 심층 설명에 넣는다.>

## 상세 설명
<코멘트 링크 또는 HTML 안내> — 코드 워크스루, 파일별 해설, 대안 검토
읽는 순서: `<핵심 파일>` → `<그 다음>` / 넘겨도 되는 파일: `<자동 생성·lock>`
```

## 심층 설명으로 내리는 것

아래는 본문에 쓰지 않는다. 전부 `explain-diff-html` 코멘트 몫이다. 본문에서 궁금해질 자리에 "상세 설명 참고" 한 줄만 남긴다.

- 코드 워크스루, 함수·클래스별 해설, diff 조각 인용
- 데이터 흐름·시퀀스·아키텍처 다이어그램
- 검토했다가 버린 대안과 비교 과정 (본문에는 채택 결론 한 줄만)
- 문제의 발생 경위·디버깅 과정·원인 분석 서사
- 여러 단계짜리 재현·검증 절차
- 파일별 변경 목록 전체 (본문은 논리 단위로 묶은 3~6줄)

## 조건부 섹션

해당될 때만 위 구조 안에 끼워 넣는다. **이것들은 승인 판단을 가르는 정보라 길어지더라도 본문에 남긴다** — 코멘트에 묻히면 안 된다. 대신 각 항목을 한두 줄로 압축한다.

**동작이 깨질 수 있을 때** — `## 호환성`: 깨지는 API·스키마·설정, 영향받는 클라이언트, 단계적 적용 계획.

**배포 순서가 중요할 때** — `## 배포`: 마이그레이션과 코드 배포 순서, 필요한 환경 변수·시크릿, 피처 플래그 이름과 기본값, 되돌리는 방법(비가역이면 명시).

**위험이 있을 때** — `## 위험과 롤백`: 잘못되면 무엇이 어디까지 망가지는지, 어떻게 감지하는지(지표·알림), 롤백 절차.

**성능·보안에 닿을 때** — 측정 결과를 숫자로 한 줄(전/후). 인증·인가·개인정보·로깅에 닿았다면 무엇을 어떻게 처리했는지 한 줄. 상세 분석은 심층 설명으로.

**화면 변경이 있을 때** — `## 화면`: Before/After 표. 이미지는 줄 수를 거의 안 먹으면서 설명을 대체하므로 본문에 두는 게 이득이다. 상호작용이 핵심이면 GIF.

**범위를 오해할 여지가 있을 때** — `### 이번 PR에서 하지 않는 것`: 한 줄씩. "이건 왜 안 했나요" 왕복을 막는 값이 분량보다 크다.
